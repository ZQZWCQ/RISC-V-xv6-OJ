### 2.2 实现步骤¶

建议按下面顺序做：

-
请先在 VSCode 中选择 File -> Open Folder...，选中 fs/newfs 目录，读一下 src/main.c。

任务一主要关注四个钩子：

- demo_mount：挂载时执行，负责初始化后续要用到的超级块信息；

- demo_umount：卸载时执行，负责做清理工作；

- demo_getattr：告诉 VFS 某个路径是什么类型，例如目录还是普通文件；

任务一只是一个很小的 demo，只要求在根目录固定显示一个文件名。因此这里先把注意力放在这四个钩子上即可，其他更完整的文件系统逻辑先不用展开。

-
先补 demo_mount()，把后续会用到的超级块信息填好。

这里最关键的是通过 ddriver_ioctl 取到：

- 磁盘总容量；

- 单次 IO 大小。

然后据此得到逻辑块大小和逻辑块总数。任务一里，一个逻辑块等于两个 IO 块，所以这里不要把 512B 当成逻辑块大小直接用。

```

}
```

-
再补 demo_readdir()，从逻辑块 500 读出那个 demo_dentry，把文件名交给 filler()。

这里的 filler() 可以简单理解成：把一个目录项名字登记到这次 ls 的返回结果里。也就是说，demo_readdir() 不需要自己直接去拼输出字符串，而是把文件名一个个交给 filler()，由 FUSE 帮你组织成目录读取结果。

这一段通常会经过下面几步：

- 根据逻辑块号算出磁盘偏移；

- 用 ddriver_seek 把磁盘头移动到对应位置；

- 用 ddriver_read 把内容读到内存；

- 从读出的数据里还原出一个 demo_dentry；

- 把其中的文件名拷到 filename，再交给 filler()。

这里可以先忽略什么，为什么？

- 任务一里，demo_readdir() 的 path、offset、fi 都可以先忽略。

{

### 3.2 实现步骤¶

simplefs 可以作为参考，但只能参考其组织方式和部分工具函数思路，不能直接照搬。

最需要注意的一点是：simplefs 的布局和本实验要求不一样。 如果直接沿用它的布局，后面的布局检查一定过不了。

命令与钩子的对应关系

必做部分至少会涉及这些钩子：

- ls：newfs_readdir、newfs_getattr

- newfs_readdir 用来读取目录下有哪些名字，newfs_getattr 用来返回文件类型、大小等属性。

- mkdir：newfs_mkdir

- newfs_mkdir 用来创建目录。

- touch：newfs_mknod、newfs_utimens

- newfs_mknod 用来创建普通文件，newfs_utimens 用来更新时间戳；有些 touch 命令会触发它。

选做部分常见会补这些钩子：

- newfs_open、newfs_opendir
 分别用于打开普通文件和打开目录。

- newfs_access
 用来检查路径是否存在、权限是否允许访问。

- newfs_read、newfs_write、newfs_truncate
 分别用于读文件、写文件，以及修改文件大小。

- newfs_unlink、newfs_rmdir
 分别用于删除普通文件和删除目录。

- newfs_rename
 用来重命名文件，或把文件 / 目录移动到新位置。

建议按下面顺序推进：

- 先定磁盘布局，并把相关字段放进超级块。

- 再封装“任意偏移、任意大小”的磁盘读写接口。

- 再明确 super、inode、dentry 的 in-Mem 和 to-Disk 结构。

- 先做 mount / umount，把首次挂载和再次挂载都跑通。

- 再做路径解析 lookup，因为后面的 getattr、readdir、mknod、mkdir 都会复用它。

- 最后补各个钩子，并且每做完一类操作就尽快手动测试。

#### 3.2.1 磁盘布局设计¶

建议先回看一下 实验原理 中关于 super_block、inode、dentry 的介绍，先分清两类结构：

- super_block_d、inode_d、dentry_d 这类 to-Disk 结构，负责“磁盘上实际存什么”；

- super_block、inode、dentry 这类 in-Mem 结构，负责“文件系统运行时在内存里怎么组织和使用这些信息”。

布局最终要写进超级块，因此超级块里至少要能描述：幻数、逻辑块大小、各区域 offset / blks，以及根目录入口。

先把两个最基本的量算出来：

- 虚拟磁盘容量是 4MB；

- 逻辑块大小是 1024B。

所以整盘一共是：

```
4MB / 1024B = 4096 个逻辑块
```

接下来要决定这 4096 个逻辑块如何分给五个区域。这里没有唯一答案，但必须满足：

- 顺序正确；

- 五个区域都存在；

- 超级块里能完整描述这套布局；

- include/fs.layout 中填写的布局要和代码里的真实布局一致。

如果你参考 simplefs，这里一定要注意它和本实验的区别：

simplefs 和本实验的核心区别

- simplefs 把一个 IO 块直接当成一个逻辑块，也就是 512B。

- 本实验的逻辑块是 1024B。

- simplefs 采用固定分配思路，没有单独的数据块位图。

- 本实验要求把 inode 区和数据块区分开，并且用数据块位图管理按需分配。

下面给一个布局估算的例子，主要是帮助你建立量级感，不是唯一答案：

一个简单的估算例子

如果你假设：

- 超级块占 1 个逻辑块；

- inode 位图占 1 个逻辑块；

- 数据块位图占 1 个逻辑块；

- 每个文件最多使用 6 个直接块；

- 为了先做粗略估算，暂时按“一个 inode_d 占一个逻辑块”来记；

可以按下面这个顺序来估：

- 先扣掉固定区域：超级块、inode 位图、数据块位图，共 3 个逻辑块；

- 整盘共有 4096 个逻辑块，所以还剩

```
4096 - 1 - 1 - 1 = 4093
```

个逻辑块给 inode 区和数据区分配；

- 每个文件最多使用 6 个数据块；

- 这里又暂时按“一个 inode_d 占一个逻辑块”来估；

- 所以一个文件连同它自己的 inode，最多大约占 6 + 1 = 7 个逻辑块。

于是，文件数量上限可以先粗略估成：

```
4093 / 7 ≈ 584
```

这说明：如果按这种最保守的估法，整个文件系统大约能支持 584 个文件。因此，inode 区更严谨的取法是先按 584 个逻辑块来留。

如果先给 inode 区留 584 个逻辑块，那么数据区还剩：

```
4096 - 1 - 1 - 1 - 584 = 3509
```

个逻辑块。

再检查一下数据区是否匹配：如果每个文件最多用 6 个数据块，那么这 3509 个数据块大约能支撑

```
3509 / 6 ≈ 584
```

个接近最大大小的文件，和前面的估算基本一致，说明这套布局在量级上是说得通的。

这个例子只是帮助你建立量级感。真实情况下，根目录、子目录、目录项本身也会占用 inode 和数据块，所以最终可支持的文件数量还会更少一些。

这里要注意，这种估法只是为了先把数量级算清楚。实际写实现时，inode_d 往往远小于 1024B，如果真的让一个逻辑块只放一个 inode_d，会显得比较奢侈；更常见的做法是一个逻辑块里放多个 inode_d。

设计好布局后，就要把这些结果真正落到挂载函数里：第一次挂载时计算并写入 super_block_d；后续再次挂载时再从磁盘读回，并恢复内存里的 super_block。大致思路如下：

```
int your_mount(struct options opt){
 ...
 if(/* 第一次挂载 */){

 /* 根据前面估算的布局，计算各区域的 offset 和 blks */

 /* 填充 super_block_d 中和布局有关的字段 */
 super_block_d.magic_num = /* 幻数 */;
 super_block_d.blk_size = /* 逻辑块大小 */;
 super_block_d.sb_offset = /* 超级块偏移 */;
 super_block_d.sb_blks = /* 超级块块数 */;

 super_block_d.ino_map_offset = /* inode 位图偏移 */;
 super_block_d.ino_map_blks = /* inode 位图块数 */;

 super_block_d.data_map_offset = /* 数据块位图偏移 */;
 super_block_d.data_map_blks = /* 数据块位图块数 */;

 super_block_d.ino_offset = /* inode 区偏移 */;
 super_block_d.ino_blks = /* inode 区块数 */;

 super_block_d.data_offset = /* 数据区偏移 */;
 super_block_d.data_blks = /* 数据区块数 */;

 super_block_d.root_ino = /* 根目录 inode 编号或入口信息 */;

 /* 初始化位图、根目录等，并把 super_block_d 写回磁盘 */
 }else{

 /* 从磁盘读回 super_block_d */

 /* 根据 super_block_d 重建内存里的 super_block */

 /* 读回位图、根目录入口等运行时需要的信息 */
 }
 ...
}
```

字段名不必和你代码里的命名完全一致，但含义上至少要分清两类：一类是需要持久化到磁盘的布局信息，另一类是只在运行时使用的内存状态。关键是第一次挂载时要把布局结果真正写进 super_block_d，后面再次挂载时才能恢复出一致的状态。

#### 3.2.2 磁盘交互的封装¶

实验框架提供的底层接口是：

- ddriver_seek

- ddriver_read

- ddriver_write

但这些接口有两个限制：

- 单次读写大小固定是一个 IO 块，也就是 512B；

- 读写起始位置也要按 512B 对齐。

所以更稳妥的做法是自己再封装一层，例如：

```
int your_read(int offset, void *out_content, int size);
int your_write(int offset, const void *in_content, int size);
```

这层封装的作用是：让上层代码以后都只关心“从哪个偏移读多少字节”，而不再反复处理 IO 对齐问题。

可以参考 simplefs，但不要直接照搬

可以参考 simplefs 的磁盘交互封装来写，但要注意两点区别：

- 本实验的逻辑块大小是 1024B，不是 512B；

- 后面超级块、位图和数据区的偏移，都要按你自己的布局来计算。

your_read() 的思路通常是：

- 根据 offset 和 size 找到覆盖该区间的对齐下界与上界；

- 用底层接口把这整段 IO 块读到中间缓冲区；

- 再把真正需要的那一段拷出来。

your_write() 则通常是标准的“读-改-写”：

- 先把受影响的 IO 块读出来；

- 在内存里改掉目标区间；

- 再整体写回去。

示意如下：

后面的超级块、位图、inode_d、目录项数组写回磁盘，都会反复用到它。把这一层先处理好，后续很多磁盘读写逻辑都会更清晰。

#### 3.2.3 文件系统接口的实现¶

在实验原理部分，我们已经介绍了文件系统中常用的几类数据结构：超级块 super_block、索引节点 inode、目录项 dentry，以及它们各自的 in-Mem / to-Disk 形式。下面给出本次实验主要接口的实现参考，同学们可以结合 simplefs 的代码来理解和完成自己的实现。

##### 3.2.3.1 挂载与卸载¶

在做这一部分之前，还需要先确定好磁盘布局，可先回看 3.2.1 磁盘布局设计。

在实验原理里已经介绍过，超级块通常要维护幻数、磁盘布局信息、根目录入口等内容。

（1）挂载函数

文件系统的 挂载函数，核心是构建并填充一个 in-Mem 版本的超级块 struct super_block，供后续整个文件系统使用。

- 如果是 第一次挂载，就需要重新初始化布局、位图、根目录等内容；

- 如果不是第一次挂载，就需要从磁盘中读取之前保存的 struct super_block_d，再恢复内存中的 struct super_block。

判断是否为第一次挂载，通常是先从预设位置读出超级块，再检查其中是否存在约定的幻数 magic_number。

为什么可以用幻数判断？

幻数就是写在超级块里的固定标记。磁盘如果已经按你的文件系统格式初始化过，这里就能读到这个值；如果是第一次挂载，或者磁盘刚被重置过，通常就读不到。

挂载时维护的 in-Mem 超级块，一般至少要包括：

- 磁盘布局信息；

- 位图的内存副本；

- 根目录入口。

```

```

本次实验无需关注挂载函数的传入参数，保持函数声明一致即可。

补充

根目录比较特殊。普通文件或目录的 dentry_d 都存放在父目录的数据块里，但根目录没有父目录，因此根目录的 dentry 往往是在挂载时单独构造出来，再与根目录的 inode 关联起来。

提示

也可以参考 simplefs 的 sfs_dump_map()，用来检查 inode 位图和数据块位图是否修改正确。

（2）卸载函数

本次实验要求支持重新挂载，因此卸载时需要把相关数据结构刷回磁盘，供下次挂载时重新读取。

文件系统的 卸载函数，主要是按照磁盘布局，把文件系统当前维护的几类结构写回磁盘：

- 超级块 struct super_block_d；

- 索引节点位图和数据块位图；

- 所有文件对应的 inode_d、目录项 dentry_d 以及必要数据。

最后，还需要关闭挂载时打开的虚拟磁盘。

卸载原理示意如下：

注意

这里的“文件”既包括普通文件，也包括目录文件。父目录的数据块里存放的是所有子文件的 dentry_d；因此，刷回目录文件的数据内容，本质上就是把它所有子文件的 dentry_d 写回到该目录对应的数据块中。

超级块和位图的写回比较直接。原因是：它们在磁盘上的位置通常是预先固定好的，挂载时也已经读入到了内存里；因此卸载时，只需要把内存中的 super_block_d、inode 位图和数据块位图，按各自约定的磁盘偏移直接写回去即可，不需要再做路径解析，也不需要遍历目录层级。

真正稍复杂的是整棵目录树的刷回。因为目录和普通文件是按层次关系组织起来的，刷回时不仅要写当前文件自己的 inode_d，还要处理它的数据内容，以及目录文件下所有子项的 dentry_d。一个常见做法是递归同步：

- 先写当前文件的 inode_d；

- 再写当前文件的数据内容；

- 如果当前文件是目录，再把它的子项 dentry_d 写回，并递归处理每个子文件。

##### 3.2.3.2 创建文件和目录¶

在文件系统中，一个文件通常至少包括三部分：索引节点 inode、目录项 dentry，以及文件数据 data。创建一个文件，首先要完成前两部分的建立和关联；普通空文件在本实验必做部分里通常还没有实际文件数据。

本次实验要求实现创建普通文件和创建目录文件，分别对应 mknod 和 mkdir 两个钩子。

普通文件和目录文件的创建流程大体一致，核心都是三步：

- 路径解析，得到父目录的 dentry；

- 创建新的 dentry，并挂到父目录下；

- 分配新的 inode，并与该 dentry 绑定。

整体流程如下图所示：

（1）路径解析，得到父目录的 dentry

先看路径解析的逻辑。在 simplefs 中，这部分对应 sfs_lookup。以路径 /hunt/bin.o 为例，解析时会从根目录开始，依次找到 hunt，再找到 bin.o 对应的 dentry。

上面介绍的是“路径存在，能够找到目标文件”的情况，这种情况通常会用于后面的查找文件和目录功能。

但在创建文件时，目标文件此时本来就还不存在。也就是说，如果路径已经能解析到对应的 dentry，反而说明重名了，应该报错；如果目标不存在，则只需要返回它的父目录 dentry，供后续创建使用。

从 dentry 到 inode 的读取也很重要。dentry 里保存了对应的 inode 编号，有了这个编号，就可以按照磁盘布局，从磁盘指定位置读出对应的 inode_d，再恢复成内存中的 inode。

如果读到的是目录文件，通常还会顺便把该目录下所有子项的 dentry_d 一起读出，并在内存中组织起来。一个常见做法是链表：父目录 inode 指向第一个子 dentry，子 dentry 再通过 brother 指向下一个兄弟项。例如：

```
struct inode {
 // ... 其他字段
 struct dentry* first_child;
}
```

```
struct dentry {
 // ... 其他字段
 struct dentry* brother;
}
```

这样就能把父目录下的所有子项串起来。simplefs 采用的也是这种链表型组织方式，本次实验完全可以参考。

目录项索引

除了链表外，现代文件系统也常用哈希表、红黑树等结构来索引内存中的目录项；但对本实验来说，链表型组织已经足够。

（2）创建新的 dentry 结构，添加到父目录

这部分在 simplefs 中可以参考 sfs_alloc_dentry。

路径解析返回父目录后，就可以创建新的 dentry，并把它加到父目录下面。如果采用前面提到的链表组织方式，一个简单做法就是头插法：让新 dentry 指向原来的第一个子项，再让父目录 inode 指向这个新 dentry。

注意

这里把子 dentry 挂到父目录 inode 上，只是文件系统运行时在内存中的组织方式。卸载时，仍然需要把这些子项重新整理成 dentry_d，再写回到父目录对应的数据块里。

如果父目录原来用于保存 dentry_d 的数据块已经放满了，可能还需要为父目录再申请新的数据块，供后续目录项写回时使用。

本实验不涉及普通文件的数据读写，因此普通空文件通常不需要立刻分配数据块；但目录文件为了将来保存子项的 dentry_d，一般需要准备数据块。数据块分配可以参考位图扫描的方式：

图中的意思是：把位图从前往后扫描，找到第一个值为 0 的位置，就说明这个数据块当前还是空闲的，可以分配给新文件或新目录；分配后，再把这一位改成 1，表示它已经被占用。

右侧代码段表达的也是这个过程：外层 byte_cursor 按字节扫描整张位图，内层 bit_cursor 再逐位检查当前字节里的 8 个 bit；if ((map_data[byte_cursor] & (0x1 << bit_cursor)) == 0) 表示“这一位还是 0，也就是找到一个空闲块”，随后用 |= 把这一位置成 1，并设置 is_find_free = TRUE 后退出循环。

（3）分配新的索引节点 inode

这部分在 simplefs 中可以参考 sfs_alloc_inode。

新创建的文件或目录都需要分配一个新的 inode。通常做法是遍历 inode 位图，找到一个空闲位，分配一个新的 inode 编号，然后构造对应的 in-Mem inode，并填写必要字段；后续卸载时，再把它写回到该编号对应的位置。

创建好 inode 后，还需要把它和前面创建的 dentry 绑定起来。类似的代码结构如下：

```
struct sfs_inode* sfs_alloc_inode(struct sfs_dentry * dentry) {
 /* 遍历索引节点位图，分配 inode */
 ...

 /* dentry 绑定该 inode */
 dentry->inode = inode;
 dentry->ino = inode->ino;
 ...
}
```

这段代码的关键在最后两行：dentry->inode = inode 是让这个目录项在内存中直接指向刚分配好的 inode；dentry->ino = inode->ino 是把对应的 inode 编号也记录下来。这样后面无论是路径解析、属性读取，还是卸载刷回磁盘，都可以通过这个 dentry 找到它对应的 inode。

通过上面三步，就可以完成创建文件和创建目录的核心逻辑。本实验不实现 . 和 ..，因此创建目录时也不要额外生成这两个特殊项。

创建普通文件对应的钩子是 .mknod，其函数原型如下：

```
int mknod(const char* path, mode_t mode, dev_t dev)
```

- path 是要创建文件相对于文件系统根目录 / 的绝对路径；

- mode 可以用来判断上层请求的文件类型；

- 本次实验不需要关注 dev 参数。

创建目录文件对应的钩子是 .mkdir，其函数原型如下：

```
int mkdir(const char* path, mode_t mode)
```

- path 是要创建目录相对于文件系统根目录 / 的绝对路径；

- mode 可以用来判断上层请求的文件类型。

##### 3.2.3.3 显示文件和目录¶

（1）获取文件属性

在显示一个文件的时候，需要查看文件的属性，如文件大小、文件类型等信息。文件的属性在 Linux 中通过一个 stat 结构体来维护。

获取文件属性的函数的核心，就是填充好对应的 stat 结构体并向上层返回。获取文件属性的函数对应 getattr 钩子。

首先进行路径解析，得到传入路径对应的 dentry 结构，然后就可以根据 dentry 及其索引的 inode 结构来填充 stat 结构体字段。一个示例如下：

```
int sfs_getattr(const char* path, struct stat * sfs_stat) {
 /* 路径解析 */
 struct sfs_dentry* dentry = sfs_lookup(path, &is_find, &is_root);

 /* 结构体填充 */
 sfs_stat->st_mode = ...;
 sfs_stat->st_size = ...;
}
```

stat 结构体通常需要填充如下一些常用字段：

结构体字段 |
字段含义 |

st_size |
文件的大小 |

st_mode |
文件的模式，包括文件的权限、文件类型 |

st_nlink |
文件的连接数，即多少硬链接 |

st_uid |
文件所有者的用户ID |

st_gid |
文件所有者的组ID |

st_blksize |
文件所在文件系统的逻辑块大小 |

st_blocks |
文件所占的块数 |

st_atime |
文件最近一次访问时间 |

st_mtime |
文件最近一次修改时间 |

以下有一些实现中的注意事项：

- 关于 st_nlink。本次实验不考虑硬链接，约定链接数均为 1。值得注意的是，根目录具有特殊性，为保证文件目录树的完整，一般文件系统会约定其链接数为 2。

- 关于 st_mode。本次实验可默认文件权限均为 0777。在 Linux 中通过 S_IFREG 表示普通文件，S_IFDIR 表示目录文件。如果想表示一个默认权限为 0777 的普通文件，其 st_mode 可以写成 0777 | S_IFREG；目录同理，可以写成 0777 | S_IFDIR。

- 关于 st_uid 和 st_gid。可以通过 getuid() 和 getgid() 获取当前用户的用户 ID 和组 ID。

获取文件属性对应的钩子函数是 .getattr，实现好显示文件属性的函数后，需要将该函数添加到 .getattr 钩子上。

.getattr 的函数原型如下，实现的显示文件属性函数要和以下声明保持一致：

```
int getattr(const char* path, struct stat * stat);
```

- path 是要读取属性的文件路径。

- stat 是要填充返回的文件属性结构体。

（2）读取目录

想要查看一个目录下有哪些文件的时候，需要用到读取目录的钩子函数。读取目录的函数主要是将 子文件的文件名 填充到 指定的缓冲区 即可。

读取目录函数主要负责的是：解析父目录路径，并根据子文件偏移 offset 获取到对应的 子文件文件名。

拿到结果之后如何返回给上层呢？读取目录函数 直接调用 上层传入的装填函数 filler 即可。上层实现并传入的装填函数 filler 决定怎么把这个结果填充到缓冲区中，和文件系统的读取目录函数无关。一个参考如下：

```
int sfs_readdir(const char * path, void * buf, fuse_fill_dir_t filler, off_t offset,
 struct fuse_file_info * fi) {
 /* 解析父目录路径 */
 struct sfs_dentry* dentry = sfs_lookup(path, &is_find, &is_root);

 if (is_find) {
 /* 根据 offset 获取到对应的子文件名 */
 sub_dentry = sfs_get_dentry(dentry->inode, offset);
 if (sub_dentry) {
 /* 直接调用 filler 来装填结果 */
 filler(buf, sub_dentry->fname, NULL, ++offset);
 }
 }
}
```

其中，filler 的原型如下：

```
int filler(void *buf, const char *name, const struct stat *stbuf, off_t off);
```

- buf 是要装填结果 name 的缓冲区。

- name 是获取到的子文件文件名。

- stbuf 无需关注，设置为 NULL 即可。

- off 是 下一个子文件 的偏移。可以把它理解成“下次应该从第几个 dentry 继续读”；也就是说，这次如果返回了当前子文件，那么传给 filler 的 off 往往就会更新成下一个目录项的位置，供后续再次调用 readdir 时继续使用。

读取目录对应的钩子函数是 .readdir，实现好读取目录的函数后，需要将该函数添加到 .readdir 钩子上。

.readdir 的函数原型如下，实现的读取目录函数要和以下声明保持一致：

```
int readdir(const char * path, void * buf, fuse_fill_dir_t filler, off_t offset, struct fuse_file_info * fi);
```

- path 是要读取的目录的路径。

- buf 是传入的装填返回结果的缓冲区。

- filler 是传入的上层自定义的装填函数。

- offset 是本次要开始读取的子文件偏移，fi 无需关注。

##### 3.2.3.4 读写文件（选做）¶

在做选做部分之前，可以先参考 simplefs 完成 newfs_open、newfs_opendir、newfs_access、newfs_truncate 这几个比较简单的钩子函数。

文件读写需要用到 read 和 write 钩子。通常先通过 lookup 找到文件对应的目录项，找到目录项之后判断文件类型，保证它是普通文件并且文件大小大于所要读取的偏移量，之后可以使用 memcpy 对内存中的文件内容进行读写。

在 simplefs 的实现中，sfs_lookup 会调用 sfs_read_inode 将索引节点读入内存，并且在内存中为 inode->data 分配空间，在 newfs 中也可以采用类似的设计。但是在本次实验中需要实现按需分配数据块，而 simplefs 是固定分配，因此 write 需要在 simplefs 的基础上增加根据写入数据长度进行磁盘数据块分配的步骤。

##### 3.2.3.5 文件与目录的删除（选做）¶

本部分需要实现 drop_inode 和 drop_dentry 这两个工具函数。drop_inode 的作用是删除内存中的一个索引结点以及该结点下的结构；对于目录类型，会递归删除子目录项对应的索引结点；对于文件类型，则会删除 inode->data。drop_dentry 的作用是从一个索引结点下，删除一个指定的目录项。在删除一个文件或目录时，先删除其本身的索引结点，再从父目录移除目录项。

```
int sfs_unlink(const char* path) {
 ...
 /* 先释放该文件对应的 inode 及其相关资源 */
 sfs_drop_inode(inode);
 /* 再把这个目录项从父目录中移除 */
 sfs_drop_dentry(dentry->parent->inode, dentry);
 return SFS_ERROR_NONE;
}
```

在 simplefs 中，drop_inode 只进行了索引结点位图的管理，在 newfs 中还需要以类似的方式管理 inode 持有的数据块。

```
int sfs_drop_inode(struct sfs_inode * inode) {
 ...

 /* 逐字节扫描 inode 位图 */
 for (byte_cursor = 0; byte_cursor < SFS_BLKS_SZ(sfs_super.map_inode_blks);
 byte_cursor++)
 {
 /* 再逐位检查当前字节中的 8 个 bit */
 for (bit_cursor = 0; bit_cursor < UINT8_BITS; bit_cursor++) {
 /* 找到与当前 inode 编号对应的那一位 */
 if (ino_cursor == inode->ino) {
 /* 将这一位清零，表示该 inode 已回收 */
 sfs_super.map_inode[byte_cursor] &= (uint8_t)(~(0x1 << bit_cursor));
 /* 标记已经找到，后面就可以退出循环 */
 is_find = TRUE;
 break;
 }
 /* 继续检查下一个 inode 编号 */
 ino_cursor++;
 }
 /* 已经完成回收，就退出外层循环 */
 if (is_find == TRUE) {
 break;
 }
 }
 ...
}
```

##### 3.2.3.6 mv命令（选做）¶

mv 的功能是重命名，或者把文件 / 目录移动到新的位置，对应的钩子函数是 newfs_rename。在 simplefs 中，一个常见思路是：先检查源路径，再在目标路径创建一个同类型的目录项，最后让目标目录项改为指向源 inode，并把原目录项从父目录中移除。

下面两段代码不是两个不同的 sfs_rename() 函数，而是同一个函数拆开的两段示意代码。

```
int sfs_rename(const char* from, const char* to) {
 ...
 /* 先检查源路径是否存在 */
 struct sfs_dentry* from_dentry = sfs_lookup(from, &is_find, &is_root);
 ...
 /* 根据源文件的实际类型，决定目的项应该按目录还是普通文件创建 */
 if (SFS_IS_DIR(from_inode)) {
 mode = __S_IFDIR;
 }
 else if (SFS_IS_REG(from_inode)) {
 mode = __S_IFREG;
 }

 /* 在目标路径先创建一个同类型的新目录项和临时 inode */
 ret = sfs_mknod(to, mode, NULL);
 /* 如果创建失败，通常说明目标不合法或已经存在 */
 if (ret != SFS_ERROR_NONE) {
 return ret;
 }
 ...
}
```

在源和目的都确认合法之后，rename 会将目标目录项原先临时创建的 inode 释放掉，再让目标目录项改为指向源 inode，最后把源目录项从原父目录移除。

```
int sfs_rename(const char* from, const char* to) {
 ...
 /* 再次拿到刚刚创建出来的目标目录项 */
 to_dentry = sfs_lookup(to, &is_find, &is_root);
 /* 释放掉目标目录项原先临时创建的 inode */
 sfs_drop_inode(to_dentry->inode);
 /* 让目标目录项改为指向源 inode */
 to_dentry->ino = from_inode->ino;
 to_dentry->inode = from_inode;

 /* 再把源目录项从原父目录中移除 */
 sfs_drop_dentry(from_dentry->parent->inode, from_dentry);
 return ret;
}
```

mv 命令看起来都像是两个参数，但它们的含义取决于第二个参数是什么：

- 如果第二个参数不是一个已存在的目录，那么它表示“新名字”；

- 如果第二个参数是一个已存在的目录，那么它表示“把源文件移动到这个目录下”。

```
$ mv f0 f1
rename /f0 /f1

$ mv f0 d0 # 这里假设 d0 已经是一个目录
rename /f0 /d0/f0
```

第一种表示“把 f0 改名为 f1”；第二种表示“把 f0 移动到目录 d0 下面”，所以目标路径会变成 /d0/f0。从 rename 钩子的角度看，它处理的始终都是“旧路径 -> 新路径”。

#### 3.3.2 实现内容¶

这一部分其实是在用一个更真实的程序负载来检验你的文件系统。数据集和模型参数都存放在文件系统上，训练脚本要从中读取数据和模型参数，并将训练后的模型参数再写回去；卸载并重新挂载之后，这些内容还应当继续保留下来。

这意味着，你前面实现的读写、持久化和容量设计，都要在这里一起经得住检验。更具体地说，你的文件系统至少要能做到：

- 稳定读取 trimmed 目录下的数据文件；

- 创建并持续更新 model/model.pth；

- 卸载并重新挂载后，之前写入的数据仍然存在；

- 支持足够大的单文件容量。

具体来说，训练脚本在获取到 MNIST 数据集后，会随机抽取其中一小部分，并对数据集进行切分，最终训练集与测试集各包含 10 个文件，分别存储在 trimmed 目录下。每个文件中存储了一个数字类别的所有样本，文件名格式为 scaled_mnist_{train/test}_{0-9}.pt。此外，训练脚本还会在 model 目录下创建一个名为 model.pth 的文件，用于存储模型参数。

在这之中，trimmed 目录下的训练集和测试集文件都只会被读取，在训练过程中不会被修改；而 model/model.pth 需要支持读写，并且会在训练过程中不断更新。

文件大小方面，trimmed 目录下的单个文件大小最大接近 1MB，而 model/model.pth 大约只有几十 KB。因此，你需要让自己的文件系统支持至少 1MB 的文件大小。简单的办法包括直接为 inode 预分配充足的数据块，或者引入间接块等机制。

间接块为什么有用？

如果你前面的 inode 设计仍然只有少量直接块指针，那么这里只靠直接块往往是不够的。比如，若逻辑块大小是 1KB，而 inode 里只有 6 个直接块指针，那么单文件容量上限就只有 6KB，显然无法存下这里接近 1MB 的数据文件。

如果逻辑块大小是 1KB，每个块指针占 4B，那么一个间接块里可以放：

```
1024 / 4 = 256 个块指针
```

这意味着只要在 inode 里增加一个间接块指针，就能额外索引 256KB 的数据；如果继续扩展更多间接层次，单文件容量还能继续增大。

传统 Unix 风格文件系统里，常见做法是采用“直接块 + 一级间接块 + 二级间接块 + 三级间接块”的组合，用多级索引逐步扩大单文件容量。现代文件系统则更常使用 extent 或树形索引结构来管理大文件，空间利用率和连续块管理通常会更好；但它们背后的核心目标是一致的，都是在保证小文件访问开销较低的同时，让大文件也能继续扩展。

常见做法主要有两种：

- 修改 inode 结构，引入间接块指针。这种做法更接近真实文件系统，空间利用率也更高；缺点是实现会复杂一些，需要连带修改多个函数，并认真处理按需分配与读写逻辑。

如果训练能跑，但卸载或重新挂载特别慢，也可以考虑加入一些优化技巧。例如给 in-Mem 结构加一个 dirty 标记；在 sync_inode() 或类似函数中，如果某个对象没有被修改，就跳过写回，从而减少不必要的磁盘写入。

#### 3.4.2 测评程序¶

我们为同学们提供了任务二的测评程序，位于 tests 目录下的 test.sh。

在开始运行测评程序之前，需要先 填写好 include 目录下的 fs.layout 文件，供测评程序使用。fs.layout 文件用于描述你的磁盘布局情况，其中 () 内的数值代表占多少个块，BSIZE 代表逻辑块大小：

```
| BSIZE = 1024 B |
| Super(1) | Inode Map(1) | DATA Map(1) | INODE(1) | DATA(*) |
```

这段配置表示文件系统如何按逻辑块划分磁盘：

- BSIZE = 1024 B：表示文件系统按 1024B 作为一个 逻辑块 来管理磁盘空间。这里说的是文件系统内部看到的块大小，不是驱动单次 IO 的大小。

- Super(1)：超级块占 1 个逻辑块。

- Inode Map(1)：inode 位图占 1 个逻辑块。

- DATA Map(1)：数据块位图占 1 个逻辑块。

- INODE(1)：inode 区占 1 个逻辑块。

- DATA(*)：其余逻辑块全部划给数据区。

测评脚本会根据这份 fs.layout 去理解你的磁盘布局，所以这里填写的块数和实际实现必须一致；否则即使代码本身没有大问题，布局检查也可能失败。

# S01 环境打通操作清单

> 目标读者：本项目开发成员
> 前置条件：一台可安装虚拟机的个人电脑
> 预计总耗时：3~5 小时（主要消耗在镜像构建与下载）

---

## 一、目标与验收标准（DoD）

**目标**：在自己机器上从零跑通「编译 → QEMU 启动 → `make grade` → 得到分数」的完整链路，并取得**真实性能数字**。

| # | 验收项 | 状态 |
|---|---|---|
| 1 | 容器内 `make qemu` 能看到 `init: starting sh` | `[ ]` |
| 2 | `./grade-lab-util -v` 能输出 `Score: x/y`（**不要加 `--toolprefix`**，见阶段 7） | `[ ]` |
| 3 | 实测三个数字：全量编译耗时 / 单次 grade 总耗时 / 单测试平均耗时 | `[ ]` |
| 4 | 三种失败路径的真实表现（空补丁 / 错误基线 / 编译错误） | `[ ]` |
| 5 | 确认 `/dev/kvm` 是否可用、QEMU 是否需要 `--privileged` | `[ ]` |

> ⚠️ **S01 不写任何业务代码。** 唯一产出是「这条链路能跑 + 耗时数字」。这些数字决定后续全部容量设计与超时阈值。

> 🚀 阶段 6~9 已有驱动脚本，在**本平台仓库根目录**执行：
>
> ```bash
> COURSE_DIR=~/rv6/xv6-oslabs-hitsz bash scripts/s01/run-s01.sh
> ```
>
> 它会依次跑完：镜像构建 → 工具链 / KVM 探测 → 全量编译计时 → QEMU 冒烟 → 判分计时 → 三条失败路径，
> 结果写进 `runtime/s01/report.md` 与 `runtime/s01/logs/`（`runtime/` 已在 `.gitignore`，不入库）。
> 下文的手工步骤仍建议走一遍，用于理解和排障。

## 二、阶段 0：宿主准备（约 30 分钟）

- 检查 CPU 虚拟化：任务管理器 → 性能 → CPU → 确认「虚拟化：**已启用**」
- 虚拟机软件：VMware Workstation Player（个人免费）
- 建议虚拟机配置：**4 核 / 8 GB 内存 / 60 GB 磁盘**
- **开启嵌套虚拟化（关键，决定 `/dev/kvm` 是否可用）**
  - VMware：虚拟机设置 → 处理器 → 勾选「虚拟化 Intel VT-x/EPT 或 AMD-V/RVI」
  - VirtualBox：`VBoxManage modifyvm "<虚拟机名>" --nested-hw-virt on`

## 五、阶段 3：安装 Docker（约 15 分钟）

> ⚠️ **不要使用 `apt install docker.io`** —— Ubuntu 仓库中的它是 snap 包，存在已知问题。使用 Docker 官方 apt 源：

```bash
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" | sudo tee /etc/apt/sources.list.d/docker.list
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker $USER     # 之后需退出重新登录
docker run --rm hello-world
```

> 国内拉取镜像慢时，可给 Docker 配置镜像加速器（`/etc/docker/daemon.json`）。
> 注意：Arch 基础镜像在部分加速器上可能缺失，若 `docker build` 报 404，先换回官方源再试。

## 八、阶段 6：跑通手工链路（核心，约 30 分钟）

**先验证「不加特权能否运行」** —— 这直接决定后续的安全设计：

```bash
docker run --rm -v ~/rv6/xv6-oslabs-hitsz:/mnt -w /mnt rv6judge:s01 \
  bash -c "make clean && time make"
```

编译通过后再启动：

```bash
docker run --rm -it -v ~/rv6/xv6-oslabs-hitsz:/mnt -w /mnt rv6judge:s01 bash
# 容器内执行：
make qemu
#   看到 "init: starting sh" 与 "$" 提示符即成功
#   退出 QEMU：按 Ctrl+A，松手，再按 X
```

> ⚠️ 若 QEMU 启动失败，**不要急于加 `--privileged`**，按序排查：
> 1. `qemu-system-riscv64 --version` —— 确认已安装
> 2. 缺少 `/dev/kvm` 不影响：QEMU 会自动回退到 TCG 纯软件模拟
> 3. **仅在确认是权限问题时**，才参照课程 Makefile 的做法加 `--privileged`

## 九、阶段 7：跑通判分（关键，约 30 分钟）

```bash
docker run --rm -v ~/rv6/xv6-oslabs-hitsz:/mnt -w /mnt rv6judge:s01 bash
# 容器内：
time ./grade-lab-util -v
```

> ⚠️ **不要给判分脚本加 `--toolprefix`。** 已读源码确认：
> `--toolprefix` **只有 `syscall` 分支的 `gradelib.py` 定义了**；
> `util` / `lock` / `pgtbl` 的 `gradelib.py` 只支持 `-v` 与 `--color`，
> 传入未知参数会被 optparse 直接拒绝（`no such option`，退出码 2），**连 `Score:` 行都不会有**。
> 工具链前缀由 Makefile 自动探测（依次尝试 `riscv64-unknown-elf-` / `riscv64-elf-` /
> `riscv64-linux-gnu-` / `riscv64-unknown-linux-gnu-`）；需要强制时用环境变量：
> `TOOLPREFIX=riscv64-elf- ./grade-lab-util -v`。

> 另两条实测事实（影响耗时口径，记录时必须注明）：
> - `gradelib.run_tests()` **开头会自己先跑一次 `make`**（增量），所以「一次 grade」的耗时包含一次增量编译；
>   而 `make grade` 目标会先 `make clean`，**耗时口径完全不同**，两者不可混记。
> - 每个测试项**各自启动一次 QEMU**（util 共 9 项 → 9 次启动），这是「单测试平均耗时」的来源，
>   也是后续并发容量估算的基本单位。

**预期输出形如：**

```
== Test sleep, no arguments == sleep, no arguments: FAIL
...
Score: 0/60
```

> ⚠️ **得到 `0/60` 才是正常的** —— 初始分支上学生代码尚未编写。
> 若连 `Score:` 行都没有，说明脚本报错，请保留完整输出。

**记录 S01 最重要的三个数字：**

| 指标 | 测量方式 | 实测值 |
|---|---|---|
| 全量编译耗时 | `make clean` 后 `time make` | |
| 单次完整 grade 耗时 | `time ./grade-lab-util -v`（含一次增量编译 + 9 次 QEMU 启动） | |
| 单测试平均耗时 | 上者 ÷ 9（util 共 9 个测试，即 9 次 QEMU 启动） | |

## 十、阶段 8：验证失败路径（约 20 分钟）

以下三条是后续「诊断模块」的原始素材，**每条都要记录真实输出**：

```bash
# ① 空补丁
: > /tmp/empty.patch
git apply --check /tmp/empty.patch ; echo "exit=$?"

# ② 基线错乱：在 syscall 分支生成补丁，拿到 util 分支上应用
git checkout syscall && git diff util-base-26 HEAD > /tmp/wrong.patch
git checkout util && git apply --check /tmp/wrong.patch ; echo "exit=$?"

# ③ 编译错误：在 user/sleep.c 中故意写入语法错误，然后 make
```

> 注意 ② 的两个细节：生成补丁时的基线 tag 必须是**util 的** `util-base-26`（模拟学生拿错基线）；
> 且空补丁 `apply --check` 会**返回 0**（能应用但什么都没改），它不算「应用失败」，
> 而属于「能构建、但拿不到分」——诊断模块需要把这两种情况区分开。

## 十二、预判会踩的坑

| 现象 | 原因 | 处理 |
|---|---|---|
| pacman 下载极慢 | 使用了国外源 | 换清华源（`infra/xv6/Dockerfile.s01` 已处理） |
| `docker build` 长时间卡在 `pacman -Syu` | Arch 为滚动更新，包体积大 | 耐心等待，或临时加 `--network=host` |
| QEMU 无输出 | 串口未接 | 使用课程 Makefile 的 `make qemu`（已含 `-nographic`） |
| `make grade` 报 Python 错误 | 镜像内 Python 版本较新 | 课程已提交过 Python 兼容补丁；若仍报错，保留 traceback |
| `/dev/kvm` 不存在 | 宿主未开启嵌套虚拟化 | 回到阶段 0 |
| 判分脚本报 `no such option: --toolprefix` | 只有 syscall 分支的 `gradelib.py` 支持该参数 | util/lock/pgtbl 只用 `-v`；需要强制前缀时用 `TOOLPREFIX=` 环境变量 |
| `docker build` 报 404 拉不到基础镜像 | 配了国内加速器但缺 `archlinux` 缓存 | 换回官方源，或指定可用的基础镜像 |

## 一、总体目标

将 xv6 实验的「提交补丁 → 编译内核 → 启动 QEMU → 跑测试 → 出分」整条链路自动化，
并补上课程目前缺失的两个环节：**提交入口**与**可读的失败诊断**。

### 重点注意事项

| 注意事项 | 解释 |
| --- | --- |
| **判分标准** | 一律复用课程已有的 `grade-lab-*` 脚本，平台只做自动化、隔离与结构化 |
| **诊断优先** | 课程脚本已经会打分；平台的价值在于**在消耗算力之前**告诉学生「补丁哪里错了」 |
| **契约先行** | 模块之间靠 `docs/03-api/` 的契约对接；接口变更务必注意先更改契约 |

### 中期检查（第 10 周前后）

**必须能演示一条完整的自动化链路**：

```
提交补丁 → 秒级预检 → 容器内应用补丁 → 编译 → 启动模拟器 → 执行判分 → 解析 → 输出得分
```

阶段产出：
- 评测镜像（可复现构建）
- 评测命令行原型 + 结果 JSON（契约 C1 定稿）
- 预检诊断规则集
- 后端数据模型与基础接口
- 学生端可演示的提交与反馈页面
- **真实性能数据**（单次评测耗时，用于容量规划）

### 结题

- 覆盖全部实验（Lab1–Lab5，含以压缩包形式提交的文件系统实验）
- 学生端与教师端功能完整，教师可导出成绩表
- 秒级预检上线，显著降低无效评测比例
- 至少 **1 个教学班**真实试用，收集反馈并完成迭代
- 交付源码、部署与运维手册、评测规范、测试用例集、结题材料
- 开源发布，配套《如何新增一门课程》文档

## 二、模块划分与分工

| 模块 | 交付物 | 依赖谁 | 被谁依赖 |

## 三、冲刺路线图

> 每轮 2 周，共 8 轮约 16 周。冲刺目标会随实际进展调整。

### S01（第 1–2 周）· 环境打通与耗时实测

**目标**：在自己机器上从零跑通「编译 → QEMU → `make grade`」，拿到真实性能数字。

| 模块 | 本轮做什么 |
| --- | --- |
| ① 评测内核 | 主力：构建评测镜像、跑通判分链路、测耗时 |
| ② 业务后端 | 装环境、读契约 C1/C2、设计数据模型草图 |
| ③ 前端 | 装环境、跑通若依模板、读契约 C2 |
| ④ 预检与部署 | 装环境、调研 `patchcheck` 的输入输出形态 |

**完成定义**：
- [ ] 容器内 `make qemu` 能看到 `init: starting sh`
- [ ] `./grade-lab-util -v` 输出 `Score: x/y`（**不要加 `--toolprefix`**，util/lock/pgtbl 的 `gradelib.py` 不认这个参数）
- [ ] 记录三个数字：全量编译耗时 / 单次 grade 耗时 / 单测试平均耗时
- [ ] 确认 `/dev/kvm` 是否可用、QEMU 是否需要特权
- [ ] 三种失败路径的真实表现（空补丁 / 错误基线 / 编译错误）

> 参考：`docs/06-runbook/S01-环境打通操作清单.md`

### S02（第 3–4 周）· 评测内核命令行原型

**目标**：把手工链路变成一条命令，并**冻结契约 C1**。

| 模块 | 本轮做什么 |
| --- | --- |
| ① 评测内核 | `rv6judge run --patch ... --lab ... --out ...` 端到端跑通；实现三级超时；评测资产回挂 |
| ② 业务后端 | 数据模型定稿；搭建 FastAPI 骨架；跑通 PostgreSQL + Alembic |
| ③ 前端 | 跑通若依前后端；确认登录与页面骨架 |
| ④ 预检与部署 | `patchcheck` 第一版（解析 unified diff + 路径白名单 + 二进制检测） |

**完成定义**：给任意一个真实补丁，一条命令能产出符合契约 C1 的 JSON；契约 C1 状态改为「定稿」。

秒级返回，不占用评测队列。

## 四、协作方式

### 分支模型

- `main` 保持可用，只接受经过评审的合并
- 功能分支：`feat/<S0n>-<简述>`，例如 `feat/S02-judge-runner`
- 修复分支：`fix/<简述>`

### 提交信息

```
<类型>(<范围>): <中文简述>
```

- 类型：`feat` `fix` `docs` `test` `refactor` `chore` `ci`
- 范围：`judge` `api` `web` `runner` `infra` `deploy` `docs`

示例：`feat(judge): 支持对 commit.patch 做路径白名单校验`

### 合并要求

1. 至少 1 人评审通过
2. 涉及接口变更的，必须先更新 `docs/03-api/`
3. 一次提交只做一件事，不把格式化与功能改动混在一起

### 契约变更规则

| 契约 | 变更流程 |
| --- | --- |
| C1（后端 ↔ 评测） | 先改 `C1-评测契约.md`；`schema_version` 递增表示不兼容变更 |
| C2（前端 ↔ 后端） | 先改 `C2-REST契约.md` 或直接改 Pydantic 模型让 `/docs` 自动更新 |

### 例会

- 每轮冲刺开头对齐本轮目标与各自任务
- 每轮冲刺结尾对照「完成定义」逐条验收
- 会议纪要放 `docs/99-meetings/`
